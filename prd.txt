
# PRD: Reward Engagement & Discussion Features for NewFreeRewards

## Objective
Enhance user engagement and content reliability by adding:
1. Love/Dislike reactions for each reward.
2. Report functionality (Expired / Not Working) for each reward.
3. Discussion section (comments) per game.

These features should integrate seamlessly into the existing Next.js project and database.

---

## 1. Love / Dislike Logic

### Description
- Users can "Love" a reward or "Dislike" it.
- Each reward shows total counts of Love and Dislike.
- Users can toggle their reaction; only one reaction per reward per user.
- Data should persist in the database and update in real-time if possible.

### Database Schema (example)
- Table: `reward_reactions`
  - `id` (PK)
  - `reward_id` (FK → rewards)
  - `user_id` (FK → users)
  - `reaction_type` (enum: "love", "dislike")
  - `created_at`, `updated_at`

### API Endpoints
- `POST /api/rewards/:id/reaction`
  - Body: `{ reaction_type: "love" | "dislike" }`
  - Logic: Toggle reaction; if same type exists, remove it.
- `GET /api/rewards/:id/reactions`
  - Returns: `{ love: number, dislike: number, user_reaction: string|null }`

### Frontend
- Show ❤️ / 👎 buttons next to each reward.
- Highlight the user’s current reaction.
- Update counts instantly when clicked.

---

## 2. Report Logic (Expired / Not Working)

### Description
- Users can report rewards as "Expired" or "Not Working".
- Reports are limited: 1 per reward per user per day.
- Admin can review reported rewards.
- Optionally, hide or mark rewards as "Needs Review" if reports exceed threshold.

### Database Schema (example)
- Table: `reward_reports`
  - `id` (PK)
  - `reward_id` (FK → rewards)
  - `user_id` (FK → users)
  - `report_type` (enum: "expired", "not_working")
  - `created_at`

### API Endpoints
- `POST /api/rewards/:id/report`
  - Body: `{ report_type: "expired" | "not_working" }`
  - Logic: Check if user already reported today; save report; return success.
- `GET /api/rewards/:id/reports`
  - Returns total report counts per type for admin review.

### Frontend
- ⚠️ Report button next to each reward.
- Opens small confirmation/modal (optional text field for notes).
- Show "Needs Review" badge if reward has multiple reports.

---

## 3. Discussion / Comments Section

### Description
- Each reward/game has its own discussion thread.
- Users can post comments, reply to others, like comments.
- Optional: use third-party (Disqus / Commento) or custom implementation.
- Pagination or lazy-loading for performance.

### Database Schema (if custom)
- Table: `reward_comments`
  - `id` (PK)
  - `reward_id` (FK → rewards)
  - `user_id` (FK → users)
  - `parent_id` (nullable FK → reward_comments for replies)
  - `content` (text)
  - `likes` (integer, default 0)
  - `created_at`, `updated_at`

### API Endpoints
- `POST /api/rewards/:id/comment`
  - Body: `{ parent_id?, content }`
- `GET /api/rewards/:id/comments`
  - Returns comments, nested replies, and likes per comment.

### Frontend
- Comment list under each reward.
- Reply button on each comment.
- Like button on each comment (optional).

---

## 4. UI/UX Suggestions

- Layout per reward:
- Reactions and report buttons should be inline, small but visible.
- Comments section should be collapsible to avoid clutter.

---

## 5. Rules & Constraints

- Only logged-in users can react, report, or comment.
- Prevent spam / abuse:
- Reactions: 1 per reward per user.
- Reports: 1 per reward per user per day.
- Comments: limit posting frequency per minute.
- Admin dashboard should show:
- Rewards flagged as "Needs Review".
- Comment moderation queue.

---

## 6. Future Enhancements (optional)

- Notify users if reward they reported is fixed.
- Leaderboard of most-loved rewards.
- User badges for reporting or commenting activity.
- Real-time updates using WebSockets for reactions and comments.

---

## 7. Dependencies

- Existing Next.js project and user authentication.
- Database: PostgreSQL / MySQL (use existing).
- Optional: Third-party discussion system (Disqus, Commento) if not custom.

---

## 8. Acceptance Criteria

1. Users can react to rewards with Love/Dislike, only one reaction at a time.
2. Users can report rewards as Expired/Not Working; system tracks reports.
3. Each reward has a discussion section where users can post and reply to comments.
4. Admin can see flagged rewards and moderate comments.
5. Reactions, reports, and comments are persisted and reflected immediately in the UI.
6. The feature does not break existing reward listing pages or database functionality.
